MySQL · 3 · 锁升级和降级

表锁、间隙锁、记录锁：锁范围什么时候变大，什么时候变小

InnoDB 在 RR 下加锁的基本单位是 Next-Key Lock（记录锁 + 间隙锁）。命中唯一索引时它会“降级”（退化）为记录锁或间隙锁；没走索引时会“升级”成锁住所有行和间隙，效果相当于锁表。但 InnoDB 不会像 SQL Server 那样把行锁自动升级成表锁，真正的表锁只来自 LOCK TABLES、DDL 和 AUTO-INC。已经加上的锁也不会降级，事务结束时才统一释放。

    方向变化触发点结果
    
        
          
    升级Next-Key → 全部行 + 间隙当前读 / UPDATE / DELETE 的条件没走索引：列上没有索引、隐式类型转换（varchar 列 = 数字）、对索引列用函数或运算、LIKE '%x'、不满足最左前缀、OR 有一边没索引、优化器认为全表扫描更快RR 下扫描到的每条记录和所有间隙（含 supremum）都被锁住，效果相当于锁表；表级其实仍然只有 IX
    
          
    升级行锁 → 表锁InnoDB 不会自动升级。只有 LOCK TABLES、DDL（MDL 写锁）、AUTO-INC 锁（innodb_autoinc_lock_mode=0，或 =1 时的批量插入）整张表被锁住；DDL 等待 MDL 写锁时，后面所有读写都会排队
    
          
    升级S → X（锁模式）同一行先 LOCK IN SHARE MODE（8.0 为 FOR SHARE）再 UPDATE；唯一键冲突的 INSERT 会先加 S 锁两个事务都持有 S、都要升级为 X → 死锁
    
          
    降级Next-Key → 记录锁唯一索引（主键 / 唯一键）等值查询，且记录存在只锁这一行，不锁间隙
    
          
    降级Next-Key → 间隙锁唯一索引等值查询但记录不存在；等值查询向右遍历到第一个不满足条件的值只锁间隙，不锁那条记录
    
          
    降级不再加间隙锁 / 提前放锁RC 隔离级别：不使用间隙锁（外键、唯一键检查除外）；不满足条件的行在 server 层过滤后立刻释放行锁没走索引时也只剩匹配行的记录锁
    
            
      
    
    
    
    
      
      
    • 已持有的锁不会降级：X 锁不会变成 S 锁，范围也不会缩小。InnoDB 是两阶段锁，事务提交或回滚时统一释放（RC 下不匹配的行是唯一的例外）。上面说的“降级”指加锁时就退化成更小的范围。
      • 
      
    • 意向锁：加行锁之前自动在表上加 IS / IX。IS、IX 之间互相兼容；IX 和表级 S、X 冲突，IS 和表级 X 冲突。作用是加表锁时只看表上的意向锁，不用逐行检查。
      • 
      
    • 为什么 InnoDB 不需要锁升级：行锁按页用 bitmap 存储，锁住很多行占用的内存也很少，所以不像 SQL Server 那样在行锁超过约 5000 个时升级为表锁。
      • 
      
    • 如何避免锁范围扩大：当前读和 UPDATE / DELETE 一定要走索引（用 EXPLAIN 检查）；能用主键或唯一索引等值命中就不用范围；可以接受幻读时用 RC；不要“先 S 后 X”，直接 FOR UPDATE；DDL 放在低峰期，先查 information_schema.innodb_trx 有没有长事务，并设置 lock_wait_timeout。
