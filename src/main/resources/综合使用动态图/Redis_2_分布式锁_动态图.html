Redis · 2 · Distributed Lock

Redis 分布式锁一定安全吗？

不一定。正确的基本写法是 SET key 唯一值 NX PX 过期时间 加锁、Lua 脚本比较后再删除。但锁过期而业务没执行完（GC 停顿）、主从切换丢锁，都会让两个客户端同时持有锁。真正保证正确性要在资源侧做校验，比如 fencing token。

    ① 锁过期了，业务还没执行完业务慢或长时间 GC 停顿，锁到期被 B 拿走，A 醒来后仍以为自己持锁看门狗续期（Redisson 默认 30s，每 10s 续期）；但解决不了 GC 停顿：停顿期间续期线程同样被暂停
    
          
    ② 主从切换导致锁丢失主从复制是异步的，锁还没同步到 Slave，Master 就宕机，新 Master 上没有锁RedLock：N（通常 5）个独立主节点，过半（≥ N/2+1）加锁成功且总耗时 < 有效期才算成功；有效时间 = 有效期 − 加锁耗时；失败时向所有节点解锁
    
          
    ③ RedLock 也有争议Martin Kleppmann：依赖时钟（时钟跳跃导致提前过期）；无法解决进程停顿和网络延迟；节点崩溃重启后丢锁（没有持久化或 fsync 不及时）不要把正确性完全交给锁
    
          
    ④ 根本思路锁服务无法知道持锁者是否“还活着”Fencing Token：锁服务发放单调递增的 token，存储拒绝比已见过更小的 token；业务等价方案：乐观锁 version、唯一约束、状态机条件更新
