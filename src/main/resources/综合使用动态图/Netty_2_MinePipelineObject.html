入口 main 的完整生命周期
main()
  ├─ run(CTX_WRITE)       → 新建 Channel → 构建 Pipeline → 注入 hello → 读取 reply:HELLO → 清理
  ├─ run(CHANNEL_WRITE)   → 新建 Channel → 构建 Pipeline → 注入 hello → 读取 reply:HELLO → 清理
  └─ run(STOP_INBOUND)    → 新建 Channel → 构建 Pipeline → inboundA 截断 → 读取 null → 清理
三个 run 按顺序独立执行，每次创建新的 EmbeddedChannel 和 Handler。正常完成前一个 run 后才会进入下一个；异常会在 finally 清理后继续向外抛出。
EmbeddedChannel 运行真实的 Netty Pipeline，本例没有启动 Spring、监听端口或发送真实网络数据。消息均为 String；页面回放针对这份示例代码，不模拟真实 socket 的线程调度。

理解与排查
为什么 ctx.writeAndFlush 不经过 outboundB？
调用发生在 business 的 Context。出站沿 prev 向前查找，先跳过 inboundB，找到 outboundA，再到 Head。outboundB 位于 business 后方，不在这次查找路径上。
write、flush、Future 和 readOutbound 是什么关系？
两个 Outbound Handler 只重写 write，因此页面列出的 OUT 日志都是 write 调用。writeAndFlush 同时发起写入与 flush；flush 沿出站方向传递，通过适配器的默认实现继续向前。在本例的 EmbeddedChannel 中，flush 后响应可从出站队列读取，写入 Promise 完成后监听器打印 success=true。这个结果不代表远端客户端已经收到数据。
runPendingTasks、checkException、finally 分别做什么？
writeInbound 返回后，入口继续调用 runPendingTasks 执行待处理任务，再调用 checkException 检查记录的异常。readOutbound 取出一条出站结果，随后与预期值比较；不一致就抛出 IllegalStateException。finally 中的 finishAndReleaseAll 负责结束 Channel 并释放队列中的剩余消息，即使前面抛异常也会执行。
后续 Handler 没执行，先检查哪里？
先看当前入站 Handler 是否调用 fireChannelRead，再看 Handler 的入站 / 出站类型和添加位置。Outbound 中要用 ctx.write(msg, promise) 继续向前转发；若在 outboundB 中改用 ctx.channel().write，操作会重新从 Tail 出发，再次进入 outboundB，可能递归。
如何在 IDEA 对照调试？
Debug MinePipelineObject.main；只看一种模式时，临时注释另外两条 run 调用。在 BP0～BP10 标记处设置断点。F8 观察业务 Handler 顺序，F7 进入传播方法，观察按入站 / 出站方向寻找下一个 Context 的过程。
